# 퉁(Toong) 서비스 기획서

문서 버전: v0.11 · 수정일: 2026-11-11

사용자가 설명한 요구사항을 바탕으로 작성한 초안입니다. ‘확정 요구사항’ 외의 화면 구성, 운영 방식, 세부 정책은 논의를 위한 제안이며 아직 확정하지 않았습니다.

## 1. 서비스 개요

**복잡한 정산, 퉁으로 끝.**

퉁은 친구들과 함께 쓴 비용을 각자의 이용 내역에 맞게 나누고, 여러 사람이 대신 결제한 금액을 합산하여 최종적으로 누가 누구에게 얼마를 보내면 되는지 알려주는 공동 정산 앱입니다.

첫 버전에서는 메뉴와 금액을 직접 입력하고 누가 무엇을 먹었는지 선택합니다. 이후 영수증·메뉴판 촬영을 추가합니다. 음식점, 카페, 노래방 등에서 결제자가 달라도 같은 모임의 지출을 함께 계산하여 서로 주고받아야 하는 돈을 간소화합니다.

## 2. 해결하려는 문제

- 친구들과 놀 때 편의를 위해 한 사람이 일행의 비용을 먼저 결제합니다.
- 사람마다 먹거나 이용한 것이 달라 단순히 인원수로 나누면 실제 부담액과 맞지 않을 수 있습니다.
- 장소마다 결제자가 바뀌면 서로 돈을 보내야 하는 상황이 생깁니다.
- 영수증 확인, 개인별 금액 계산, 여러 결제 내역 합산을 수동으로 처리하기 번거롭습니다.

## 3. 확정 요구사항

| 구분 | 요구사항 |
| --- | --- |
| 서비스 이름 | 퉁(Toong), 저장소 이름 `toong` |
| 개발 방향 | Flutter / Dart로 모바일 앱부터 개발. 웹 선출시 후 앱 전환 방식은 채택하지 않음 |
| 입력 방식 | 첫 버전은 메뉴·금액 수동 입력. 영수증·메뉴판 촬영과 인식은 후속 단계 |
| 개인별 배분 | 누가 어떤 메뉴를 먹었는지 체크하여 부담액 계산 |
| 친구 연동 | 친구들이 함께 정산 정보를 공유하고 연결되는 기능 |
| 비회원 연결 | 계정 가입·로그인 없이 방 생성 가능. 생성된 방 코드를 친구가 입력하면 같은 방에 참여 |
| 방 링크 공유 입장 | 방 코드 입장은 유지하고, 방 링크를 복사·공유해 그 링크로 입장하는 방법 추가. 구현 완료 |
| 게스트 이용 안내 | 방 생성·입장 전에 앱 삭제·기기 변경 등으로 기존 참여 권한을 잃을 수 있음을 미리 안내 |
| 정산 복제 | 방장 권한을 잃은 경우에도 기존 참여자가 읽을 수 있는 방의 정산을 새 방으로 복제하고 새 방장이 될 수 있음 |
| 시작 화면 | `복잡한 정산, 퉁으로 끝.` 문구와 `새방 만들기`, `방 코드로 입장`, `참여중인 방 목록` 버튼 세 개로 구성 |
| 시작 화면의 지난 방 접근 | `참여중인 방 목록` 버튼으로 별도 목록 화면에 이동 |
| 로딩 화면 | 추후 제작 |
| 여러 결제자 | 같은 모임에서 A와 B 등 여러 사람이 각각 결제한 지출 처리 |
| 정산 간소화 | 서로에게 줄 돈과 받을 돈을 상계하여 최종 정산 금액 안내 |
| 잔돈 처리 | 첫 버전은 최종 정산 전 남은 금액을 표시하고 부담자 한 명을 직접 선택. 후보 추첨·가챠·사다리타기는 후속 단계 |
| 초기 목표 | 계산 및 친구 간 연동 구현 |
| 앱 내 송금 | 제공 여부 미정 |

## 4. 주요 사용자와 사용 상황

친구들과 식사, 카페, 노래방 등 여러 활동을 함께하고 비용을 나누는 사람들을 우선 대상으로 합니다.

대표 상황은 ‘A가 음식점에서 결제하고 B가 노래방에서 결제한 뒤, 각자의 이용 내역을 반영해 모임 전체를 한 번에 정산하는 경우’입니다.

## 5. 핵심 사용 흐름 — 제안

1. 사용자가 게스트 이용 시 재접속 권한을 잃을 수 있다는 안내를 확인하고, 계정 가입 없이 닉네임을 입력해 정산 방을 만듭니다. 방 코드가 발급되면 친구들에게 전달하고, 친구들도 같은 안내를 확인한 뒤 코드와 닉네임으로 참여합니다.
2. 지출의 장소, 메뉴, 수량, 금액을 직접 입력합니다.
3. 입력한 항목과 총액을 확인하고 필요한 부분을 수정합니다.
4. 실제 주문한 항목과 각 항목을 먹은 사람을 선택합니다.
5. 해당 지출을 실제로 결제한 사람과 결제 금액을 기록합니다.
6. 다른 친구가 결제한 지출도 같은 모임에 추가합니다.
7. 최종 정산 직전에 나누고 남은 금액을 확인하고 항목별 부담자 한 명을 직접 선택합니다.
8. 잔돈 처리 결과를 반영해 각자의 부담액과 대신 결제한 금액을 합산합니다.
9. 최종적으로 누가 누구에게 얼마를 보내야 하는지 확인합니다.

초기 버전에서 실제 송금은 앱 외부에서 이루어지는 흐름을 제안합니다. 송금 완료를 사용자가 표시하는 기능은 별도로 도입 여부를 결정합니다.

## 6. 기능 상세 — 제안

### 6.1 방 코드 기반 비회원 연결 및 모임 연동

- 가입·로그인 없이 ‘방 만들기’와 ‘방 코드로 참여하기’를 제공합니다.
- 방을 만든 사람은 방장이 되며, 생성된 코드를 친구에게 공유합니다. 코드를 입력한 친구는 기존 방에 입장하며 별도의 방을 만들지 않습니다.
- 방 코드와 함께 방 링크도 복사·공유할 수 있습니다. 링크를 누르면 앱이 열리고 닉네임만 입력해 같은 방에 입장합니다. 링크는 방 코드를 담은 초대 수단이며, 코드 입장과 같은 게스트 안내·입장 제한·48시간 삭제 규칙을 따릅니다. 링크 형식은 앱 전용 주소 `toong://join/방코드`입니다. 이미 참여한 방의 링크는 안내 없이 바로 그 방을 엽니다. 앱이 없는 기기에서는 링크가 열리지 않으므로 방 코드 입장을 함께 안내합니다. 구현 완료.
- 화면에는 닉네임으로 참여자를 표시하는 방식을 제안합니다. 닉네임과 별개인 내부 참여자 ID로 결제자와 부담자를 구분합니다.
- 정산 방 하나를 모임 하나로 보고 참여자와 지출 내역을 관리합니다.
- 참여자는 같은 지출과 정산 결과를 확인하고 잔돈 처리 결과도 공유합니다.
- 내역이 바뀌면 참여자에게 최신 계산 결과를 공유합니다.
- 새로 입장한 사람은 이미 등록된 지출과 항목의 부담자·잔돈 추첨 후보에 자동 포함하지 않습니다. 해당 항목에서 직접 선택한 경우에만 포함합니다.
- 방장 권한을 잃어 기존 방을 관리할 수 없으면, 기존 방에 입장할 수 있는 참여자가 `이 방의 정산 복제하기`로 새 방을 만들 수 있습니다. 복제한 사람이 새 방의 방장이 됩니다.

비회원 방 생성·코드 참여는 확정 요구사항입니다. 계정 기반 친구 목록이나 계정 로그인은 필수 진입 절차로 두지 않으며, 추가 제공 여부와 방식은 미정입니다. 초기에는 방장이 지출을 관리하고 참여자는 자기 배분을 확인하는 방식부터 검토할 수 있습니다.

**방 코드와 재접속 세부 정책 — 제안:**

- 코드는 서버에서 중복되지 않게 생성합니다. 혼동하기 쉬운 문자를 제외한 영문·숫자 6~8자 형식을 후보로 두며 정확한 길이는 구현 전에 결정합니다.
- 잘못된 코드 또는 참여가 닫힌 방에는 입장할 수 없고 안내 메시지를 표시합니다. 코드가 틀렸다고 새 방을 자동 생성하지 않습니다.
- 유효한 코드로 입장하면 서버에 참여 관계를 저장하고, 이후 데이터 조회·수정 권한은 그 참여 관계로 확인합니다. 방 코드는 초대 수단이며 기존 참여자의 신원을 복구하는 수단으로 사용하지 않습니다.
- 방 코드를 아는 사람은 참여할 수 있다는 점을 공유 화면에 안내합니다. 서버에서 입장 시도 횟수를 제한하고, 방장의 신규 참여 잠금과 코드 재발급 기능을 검토합니다.
- 앱에 게스트 세션을 보관하여 같은 기기에서 앱을 다시 열어도 기존 참여자로 이어갑니다. 반복 입장 요청이 중복 참여자를 만들지 않도록 합니다.
- 같은 닉네임을 입력해도 다른 사람의 기존 참여자 정보나 방장 권한을 가져올 수 없습니다. 표시 이름 중복은 방 안에서 구분되도록 처리합니다.
- 방 생성·입장 전에 앱 삭제·데이터 초기화·기기 변경 시 기존 게스트 참여 권한을 잃을 수 있고, 방 코드나 닉네임만으로 이전 참여자·방장 권한을 되찾을 수 없음을 안내합니다. 같은 기기의 세션이 남아 있으면 다시 들어갈 수 있습니다.
- 방장 앱이 잠시 꺼져도 방과 지출은 서버에 유지합니다. 방장 권한을 잃은 경우 기존 참여자가 정산을 복제해 새 방에서 이어갈 수 있습니다. 복제는 원래 방의 방장 신원이나 권한을 복구하지 않습니다.
- 정산을 완료하지 않은 채 48시간 동안 입력이 없는 방은 자동으로 삭제합니다. 자세한 내용은 6.8을 따릅니다. 코드 만료, 정산 완료 후 신규 참여 허용 여부는 추후 결정합니다.

**정산 복제 정책 — 제안:**

- 방에 이미 참여해 읽기 권한이 있는 사람만 복제할 수 있습니다. 원본 방과 정산 내역은 유지하며, 새 방 코드와 별도의 복제본을 만듭니다.
- 지출·메뉴·금액·결제자·부담자 기록을 복사하고 새 방에서 다시 계산합니다. 이전 방의 송금 완료 여부나 게스트 세션·방장 권한은 복사하지 않습니다.
- 과거 참여자의 이름·결제자·계산상 몫을 보존하되, 복제만으로 새 방의 실제 참여자로 인증하지 않습니다. 새 방장은 자기 과거 기록을 선택해 연결하고, 다른 사람들은 새 코드로 입장한 뒤 기존 기록과 연결하는 흐름을 제안합니다.
- 다시 입장하지 못한 사람의 과거 기록도 계산에서 유지합니다. 최종 정산 전에 연결되지 않은 사람과 송금 대상·금액을 확인하도록 표시합니다. 복제된 이름만으로 기존 참여자의 권한을 부여하지 않습니다.
- 최초 버전에서 복제 버튼을 방장에게도 보일지, 복제본에서 수정 가능한 범위와 기록 연결 방법은 구현 전에 정합니다.

### 6.2 영수증 촬영 — 후속 단계

영수증에서 메뉴명, 수량, 항목별 금액, 총액 등의 정보를 추출하는 기능을 제안합니다. 사진 인식 결과는 사용자가 확인하고 수정할 수 있어야 합니다.

영수증의 ‘단가’와 ‘수량이 반영된 항목 합계’를 구별하여 수량이 두 번 곱해지는 오류를 방지합니다. 항목 합계와 실제 결제액이 다르면 차이를 표시하고 사용자가 해결하도록 합니다.

### 6.3 메뉴판 촬영 — 후속 단계

메뉴판에서 메뉴명과 가격을 추출한 뒤 실제 주문한 메뉴와 수량을 선택합니다.

메뉴판에는 실제 주문 내역이나 결제 총액이 없으므로, 촬영만으로 정산을 확정하지 않습니다. 주문 선택과 실제 결제액 확인 단계를 거칩니다. 옵션, 할인 등으로 메뉴판 가격과 결제액이 다르면 수정할 수 있어야 합니다.

### 6.4 개인별 메뉴 배분

- 개인 메뉴: 해당 메뉴를 먹은 한 명에게 비용을 배정합니다.
- 공유 메뉴: 함께 먹은 사람들을 선택하고, 기본적으로 선택한 사람끼리 균등 배분합니다.
- 공동 이용료: 노래방처럼 메뉴가 없는 지출은 금액을 직접 입력하고 참여자끼리 나눕니다.
- 미배정 항목: 부담할 사람이 없는 항목을 표시하고 정산 확정 전에 해결합니다.

한 항목을 수량별로 나누거나 서로 다른 비율로 부담하는 기능은 추가 검토 사항입니다. 초기에는 항목을 분리하여 각자에게 배정하는 방식도 가능합니다.

### 6.5 결제자 기록

각 지출에는 실제 결제자와 실제 결제액을 기록합니다. 결제자와 그 지출에 참여한 사람은 구분합니다. 한 사람이 대신 결제했더라도 비용은 실제로 먹거나 이용한 사람에게 배정합니다.

초기에는 지출 한 건당 결제자 한 명을 지원하는 방식을 제안합니다. 한 결제 건을 여러 사람이 나눠 결제하는 기능은 추후 검토합니다.

### 6.6 통합 정산

모임 내 모든 지출을 합산하여 개인별 순잔액을 계산합니다.

**개인별 순잔액 = 실제 결제한 금액 합계 − 본인이 부담할 금액 합계**

- 순잔액이 양수이면 해당 금액을 받아야 합니다.
- 순잔액이 음수이면 해당 금액의 절댓값을 보내야 합니다.
- 순잔액이 0이면 추가로 주고받을 돈이 없습니다.

이 잔액을 기준으로 받을 사람과 보낼 사람을 연결해 송금 안내를 만듭니다. 예를 들어 서로 2만 원과 1만 원을 보내야 한다면 차액 1만 원만 보내도록 안내합니다.

방 상세의 `정산 결과 보기` 버튼 위에 아직 처리하지 않은 `남은 잔돈 N원`을 표시합니다. 최종 정산을 요청했을 때 처리되지 않은 잔돈이 있으면 잔돈 처리 화면을 먼저 보여줍니다. 모든 잔돈의 부담자가 정해진 뒤에만 최종 순잔액과 송금 안내를 확정합니다. 처리 전에는 개인별 부담액과 정산 결과를 임시 계산으로만 표시합니다.

여러 명의 정산에서는 원래 대신 결제해 준 상대와 최종 수취인이 달라질 수 있습니다. 화면에서 이 방식과 계산 근거를 설명하는 것을 제안합니다. 모든 경우에 수학적으로 가장 적은 송금 횟수를 보장할지는 별도 결정 사항이며, 초기 목표는 잔액을 정확하게 유지하면서 불필요한 왕복 송금을 줄이는 것입니다.

### 6.7 잔돈 처리 — 가칭 ‘잔돈 퉁!’

**첫 버전 확정 요구사항:** 최종 정산 전에 나누어떨어지지 않아 남는 금액을 보여주고, 각 잔돈을 부담할 사람 한 명을 직접 선택합니다. 선택이 끝나면 최종 정산을 진행합니다.

**후속 단계 확정 방향:** 직접 지정 외에 추첨을 추가합니다. 추첨 전에 후보자를 고르고 `모두 선택` 기능을 제공하며, 연출은 랜덤 선택 가챠 또는 사다리타기 중에서 결정합니다.

**세부 동작 제안:**

- 나누는 항목별로 기본 부담액을 원 단위로 내림하고, 남은 금액 전체를 한 명에게 배정합니다.
- 최종 정산 직전에 잔돈의 총합과 잔돈이 발생한 항목별 금액을 보여줍니다. 합계는 안내용이며, 실제 배정은 항목별로 처리합니다.
- 각 항목에서 잔돈을 부담할 수 있는 사람은 그 항목의 부담자로 선택된 참여자입니다. 방에 늦게 들어온 사람도 해당 항목에 직접 추가한 경우에만 후보로 선택할 수 있습니다.
- 첫 버전에서는 해당 항목의 부담자 한 명을 선택하여 잔돈 전체를 부과합니다. 후보 선택과 `모두 선택`은 추첨 기능을 추가할 때 도입합니다.
- 나머지가 0원이면 잔돈 처리 화면을 건너뜁니다. 여러 항목에 잔돈이 생기면 항목별로 부담자를 지정합니다.
- 직접 지정 결과는 모든 참여자가 공유합니다. 앱을 다시 열거나 다른 기기에서 봐도 동일하며, 동시에 처리해도 해당 항목에 하나의 결과만 적용합니다.
- 금액이나 배분 참여자가 바뀌면 영향받는 항목의 기존 결과를 무효화하고 다시 처리해야 함을 표시합니다.
- 선택된 사람의 부담액에 잔돈을 더한 뒤 전체 순잔액과 최종 송금 안내를 확정합니다.

**후속 추첨 규칙 — 제안:** 추첨을 시작하기 전에 한 명 이상의 후보를 고릅니다. `모두 선택`은 해당 항목의 부담자 전원을 선택하거나 해제합니다. 후보들은 같은 확률로 선택합니다. 랜덤 가챠 또는 사다리타기로 한 사람을 뽑고 결과를 모든 참여자에게 공유합니다. 후보가 한 명이면 연출 없이 바로 배정하는 방식을 검토합니다. 같은 금액·참여자 구성의 결과를 임의로 다시 뽑지 않는 방향을 제안합니다.

예를 들어 **10,000원을 3명이 나누면** 기본 부담액은 각 3,333원이고 잔돈은 1원입니다. 첫 버전에서 B를 지정하면 A 3,333원, B 3,334원, C 3,333원이 됩니다.

**10,001원을 3명이 나누면** 잔돈 2원 전체를 지정된 한 명이 부담합니다. B를 지정하면 A 3,333원, B 3,335원, C 3,333원입니다. 이 기능은 원 단위 나눗셈의 나머지에 적용하며, 입력 오류나 누락으로 생긴 금액 차이는 지출 내역을 수정하여 해결합니다.

### 6.8 방 자동 삭제, 얼리기·연장, 정산 기록 — 사용자 확정, 구현 완료

**방향:** 서버 저장은 최소로 합니다. 서버의 방은 정산이 진행되는 동안만 쓰는 임시 공간이고, 완료된 정산 기록은 서버가 아니라 각자의 기기에 텍스트로 남깁니다. 체험 모드(기기 저장)에도 같은 규칙을 적용합니다.

**방이 삭제되는 시각**

| 방 상태 | 삭제 시각 |
| --- | --- |
| 진행 중 | 마지막 입력 48시간 뒤 |
| 얼린 방 | 얼린 지 7일 뒤. 그 전에 녹이면 그때부터 48시간 |
| 정산 완료한 방 | 완료 12시간 뒤 |

- 입력으로 보는 동작: 방 생성, 참여자 입장, 지출·항목·부담자·잔돈 지정 저장, 과거 기록 연결, 방 연장. 방을 열어 보기만 하는 것은 입력으로 보지 않습니다.
- 삭제 시각이 지난 방은 삭제 작업이 돌기 전이라도 목록에서 숨기고, 입장·수정·복제를 막습니다.
- 복제로 만든 방은 새 방이므로 48시간을 새로 세고, 원본의 연장 횟수·얼림·완료 상태를 물려받지 않습니다. 원본 방이 삭제되어도 복제본은 남습니다.
- 게스트 이용 안내와 방 상세 화면에 삭제 규칙과 삭제까지 남은 시간을 보여줍니다.

**방 연장**

- 방장이 `연장`을 누르면 남은 시간이 48시간으로 돌아갑니다.
- 방 하나당 3회까지입니다. 남은 횟수를 버튼에 보여줍니다.

**방 얼리기**

- 방장이 방을 얼리면 삭제 시간이 멈춥니다. 얼린 동안에는 지출 입력, 새 참여자 입장, 연장, 정산 완료를 막습니다. 이미 참여한 사람은 방을 볼 수 있고, 복제도 할 수 있습니다.
- 한 사람(게스트 세션, 즉 기기)이 동시에 얼려 둘 수 있는 방은 2개입니다. 녹이거나 방이 삭제되면 자리가 납니다.
- 얼린 방은 7일 안에 녹이지 않으면 삭제됩니다. 서버에 방이 무기한 남지 않게 하기 위한 제한입니다.
- `참여중인 방 목록`에서 얼린 방을 표시합니다.

**정산 완료와 텍스트 기록**

- 지출이 하나 이상 있고 잔돈이 모두 처리된 뒤 방장이 `정산 완료`를 누를 수 있습니다.
- 완료된 방은 더 이상 수정·입장할 수 없고 12시간 뒤 서버에서 삭제됩니다. 고칠 내용이 있으면 `이 방의 정산 복제하기`로 새 방을 만듭니다. 완료 취소는 제공하지 않습니다.
- 그 방에서 있었던 모든 거래를 텍스트로 기록합니다. 방 정보, 참여자, 지출마다 결제자와 항목·금액·부담자·잔돈 부담자, 개인별 결제액·부담액·순잔액, 최종 송금(누가 누구에게 얼마)을 담습니다.
- 기록은 서버에 저장하지 않습니다. 완료된 방이나 방 목록을 연 기기에 저장되므로, 참여자는 완료 후 12시간 안에 방을 열어야 자기 기기에 기록이 남습니다. 방장은 기록을 복사해 메신저로 공유할 수 있습니다.
- 기기에 저장된 기록은 앱 삭제·기기 변경 시 사라진다는 점을 목록에 안내합니다. 기록은 기기에서 직접 지울 수 있습니다.
- `참여중인 방 목록` 안에서 `진행 중인 방`과 `완료된 정산 기록`을 구분해 보여줍니다. 시작 화면 버튼은 늘리지 않습니다.

기록 예시:

```text
[퉁 정산 기록] 저녁 모임 (방 코드 ABC1234)
정산 완료: 2026-11-11 22:10 · 방장 A
참여자: A, B, C
총액: 90,001원

1. 음식점 · 결제 A · 60,000원
   - 스테이크 25,000원 · A
   - 파스타 20,000원 · B
   - 샐러드 15,000원 · C
2. 노래방 · 결제 B · 30,001원
   - 이용료 30,001원 · A, B, C (각 10,000원) · 잔돈 1원 B 부담

개인별 정산
- A: 결제 60,000원 · 부담 35,000원 · +25,000원
- B: 결제 30,001원 · 부담 30,001원 · 0원
- C: 결제 0원 · 부담 25,000원 · -25,000원

최종 송금
- C → A 25,000원
```

**서버에 저장하는 것**

- 방마다 삭제 시각 하나와, 방 내용 안의 연장 횟수·얼린 시각·완료 시각뿐입니다. 정산 기록은 저장하지 않습니다.
- Supabase `pg_cron`으로 1시간마다 삭제 시각이 지난 방을 지웁니다.
- 참여 중인 방이 하나도 없는 익명 사용자는 하루 한 번 지웁니다. 막 만들어진 사용자가 방을 만들기 전에 지워지지 않도록 만든 지 48시간이 지난 사용자만 대상입니다. 지워진 사용자의 기기는 다음에 방을 만들거나 입장할 때 새 익명 사용자로 자동 로그인합니다.

**남은 결정 사항:**

- 삭제 전 알림 여부
- 얼린 방에서 지출 입력을 허용할지(지금은 녹여야 입력 가능)

## 7. 정산 예시

A, B, C가 함께 식사와 노래방을 이용했다고 가정합니다.

| 지출 | 실제 결제자 | 총액 | A 부담 | B 부담 | C 부담 |
| --- | --- | ---: | ---: | ---: | ---: |
| 음식점 | A | 60,000원 | 25,000원 | 20,000원 | 15,000원 |
| 노래방 | B | 30,000원 | 10,000원 | 10,000원 | 10,000원 |
| 합계 | — | 90,000원 | 35,000원 | 30,000원 | 25,000원 |

| 사람 | 실제 결제액 | 본인 부담액 | 순잔액 |
| --- | ---: | ---: | ---: |
| A | 60,000원 | 35,000원 | +25,000원 |
| B | 30,000원 | 30,000원 | 0원 |
| C | 0원 | 25,000원 | −25,000원 |

최종 안내는 **C → A: 25,000원**입니다. B는 음식점에서 A에게 줄 돈과 노래방에서 받을 돈이 상쇄되어 추가 송금이 필요 없습니다.

## 8. 단계별 개발 범위

### 1단계: 수동 입력 첫 버전 — 사용자 확정

- 가입 없는 게스트 식별, 닉네임 설정, 방 코드 공유·입장
- 정산 방 생성 및 참여자 관리, 같은 기기의 기존 세션 재접속
- 방 생성·입장 전 게스트 이용 및 세션 분실 주의 안내
- 기존 참여자가 `이 방의 정산 복제하기`로 새 방을 만드는 흐름
- 직접 입력하는 지출 등록
- 메뉴별 참여자 선택과 기본 균등 배분
- 최종 정산 전 잔돈 표시, 부담자 직접 선택, 결과 공유
- 지출별 결제자 기록
- 여러 지출의 개인별 부담액 및 순잔액 계산
- 최종 송금 대상과 금액 안내
- 참여자 간 정산 내역 공유

### 2단계: 사진 입력 — 진행 순서 제안

- 영수증·메뉴판 촬영과 항목 인식
- 인식 결과 확인·수정 후 수동 입력과 같은 계산 흐름에 연결

### 3단계: 잔돈 추첨 — 진행 순서 제안

- 추첨 후보 선택 및 `모두 선택`
- 가챠 또는 사다리타기 중 한 가지 추첨 연출부터 제공
- 모든 참여자에게 같은 결과 공유

### 당분간 보류할 기능

- 앱 내 직접 송금 및 금융 계좌 연동
- 다중 통화 정산
- 복잡한 가중치·비율 배분
- 한 지출의 여러 결제자 처리
- 자동 독촉, 장기 미정산 관리, 지출 통계

2·3단계의 순서는 개발 제안이며, 사진 입력과 잔돈 추첨을 나중에 추가한다는 방향은 확정됐습니다. 앱 내 송금의 최종 제공 여부는 확정하지 않았습니다.

## 9. 화면 구성 — 제안

| 화면 | 주요 내용 |
| --- | --- |
| 시작·홈 | `복잡한 정산, 퉁으로 끝.` 문구와 `새방 만들기`, `방 코드로 입장`, `참여중인 방 목록` 버튼 세 개 |
| 참여중인 방 목록 | 이전에 참여한 방들을 보여주고, 선택한 방으로 이동 |
| 방 만들기 | 닉네임과 방 이름 입력, 생성된 방 코드·방 링크 확인·복사·공유 |
| 방 코드로 참여 | 코드와 닉네임 입력, 입장 결과와 오류 안내 |
| 게스트 이용 안내 | 방 생성·입장 진행 중 세션 분실 시 기존 참여자·방장 권한을 복구할 수 없다는 안내 |
| 모임 상세 | 방 코드, 방장과 참여자, 지출 목록, 결제 총액, `정산 결과 보기` 버튼 위의 미처리 잔돈 총액, `이 방의 정산 복제하기` 진입 |
| 정산 복제 | 새 방 생성, 복사할 내역 확인, 새 코드 공유, 참여자 재입장·기록 연결 및 미연결 기록 확인 안내 |
| 지출 등록 | 1단계 직접 입력. 영수증·메뉴판 촬영은 2단계에서 추가 |
| 항목 확인·배분 | 메뉴·가격·수량 수정, 먹은 사람 선택, 결제자 지정 |
| 잔돈 퉁! | 1단계에서 잔돈 총합·항목별 잔돈 표시와 부담자 직접 선택. 3단계에서 추첨 후보 선택·모두 선택·추첨 추가 |
| 정산 결과 | 각자 결제액·부담액·순잔액, 최종 송금 안내 |

**시작 화면 확정 구성:**

```text
복잡한 정산, 퉁으로 끝.

새방 만들기
방 코드로 입장
참여중인 방 목록
```

이 네 문구 외의 시작 화면 콘텐츠는 현재 범위에 포함하지 않습니다. 로딩 화면은 추후 제작합니다. `참여중인 방 목록` 버튼을 누르면 별도 목록 화면에서 이전에 참여한 방을 선택합니다. 목록의 상세 표시 정보와 빈 상태는 추후 디자인합니다. 방을 선택했을 때 보관된 게스트 세션으로 재입장하며, 세션이 유효하지 않으면 다른 참여자로 자동 연결하지 않고 안내합니다.

## 10. 정산 정확성과 예외 처리 — 제안

- 초기 통화는 원화로 하고, 금액은 정수 원 단위로 처리합니다.
- 나누어떨어지지 않는 금액은 기본 부담액을 원 단위로 내린 뒤, 남은 금액 전체를 1단계에서는 직접 지정된 한 명에게 배정합니다. 3단계부터 추첨도 지원합니다.
- 처리되지 않은 잔돈이 하나라도 있으면 최종 정산과 송금 안내를 확정하지 않습니다.
- 모든 개인 부담액의 합계는 실제 결제 총액과 같아야 합니다.
- 모든 개인 순잔액의 합계는 0원이어야 합니다.
- 안내된 송금을 모두 수행한 뒤 모든 사람의 잔액이 0원이 되어야 합니다.
- 할인, 쿠폰, 추가 요금으로 합계가 달라지면 조정액의 부담 방식을 확인한 뒤 계산합니다.
- 사진 기능을 도입하는 2단계에서는 인식 실패 시 재촬영과 수동 입력으로 진행할 수 있어야 합니다.
- 2단계에서는 이미 등록한 영수증을 다시 등록할 때 중복 지출 확인 흐름을 검토합니다.
- 정산 후 지출 수정이나 일부 송금이 이루어진 경우의 재계산 정책은 별도로 정합니다. 초기에는 확정 전 계산 흐름을 우선 구현하는 것을 제안합니다.

## 11. 데이터와 공유 정책 — 제안

기본 관리 대상은 게스트 사용자·세션, 정산 방, 방 코드, 방별 참여자와 역할, 지출, 메뉴 항목, 항목별 부담 내역, 정산 결과, 잔돈 처리 결과, 복제된 방의 원본 참조입니다. 계정과 지속적인 친구 관계는 선택 기능으로 별도 검토합니다. 잔돈 처리 결과에는 대상 항목과 배분 버전, 처리 방식(1단계 직접 지정, 3단계 추첨 추가), 잔돈 금액, 선택된 사람, 확정 시점을 기록하는 것을 제안합니다. 추첨 도입 시 후보 목록도 기록합니다.

모임 내역은 해당 모임 참여자에게만 공유하는 것을 기본으로 제안합니다. 정산 복제는 원본 방에 참여 중인 사람에게만 허용합니다. 2단계에서 영수증 사진을 도입할 때는 정산과 무관한 정보가 포함될 수 있으므로 사진 원본의 공유 범위와 보관 기간을 정해야 합니다.

각 지출의 작성자와 수정 시점을 기록하고, 누가 어떤 내역을 수정할 수 있는지 정합니다. 동시에 수정할 때 다른 참여자의 변경을 덮어쓰지 않도록 처리해야 합니다.

## 12. 단계별 완료 판단 기준 — 제안

**1단계 수동 입력 첫 버전**

1. 가입·로그인 없이 한 기기에서 방을 만들고, 다른 기기에서 방 코드와 닉네임으로 같은 방에 참여하여 동일한 지출·정산 결과를 볼 수 있습니다.
2. 방 생성·입장 전에 게스트 세션을 잃으면 기존 권한을 복구할 수 없다는 안내를 볼 수 있습니다.
3. 메뉴 또는 공동 이용료를 직접 입력하고 부담자를 선택할 수 있습니다.
4. 결제자가 여러 명인 모임에서 각자의 부담액과 순잔액이 정확하며, 위 예시에서 C가 A에게 25,000원을 보내는 결과가 나옵니다.
5. 10,000원·10,001원을 각각 3명이 나눌 때 최종 정산 전에 잔돈 1원·2원을 보여주고, 직접 지정한 한 명에게 해당 잔돈 전체가 반영됩니다.
6. 잔돈이 없으면 처리 화면을 생략하고, 잔돈이 처리되지 않았으면 최종 정산을 확정할 수 없습니다.
7. 지출 금액이나 부담자가 바뀌면 영향받는 잔돈 지정 결과를 다시 확인하고, 모든 개인 부담액 합계와 결제 총액이 일치합니다.
8. 모임 비참여자는 해당 모임의 내역을 볼 수 없습니다. 잘못된 코드로는 입장하거나 새 방을 만들 수 없습니다.
9. 같은 게스트 세션의 재접속·반복 입장은 기존 참여자로 이어지고, 닉네임만 같다고 다른 참여자나 방장 권한을 얻을 수 없습니다.
10. 늦게 입장한 사람은 기존 지출의 부담자에 자동 포함되지 않습니다.
11. 기존 참여자가 원본 방의 정산을 새 방으로 복제할 수 있고, 복제한 사람이 새 방장이 됩니다. 원본은 유지됩니다. 재입장하지 못한 과거 참여자의 결제액·부담액도 계산에 남고, 미연결 기록은 최종 정산 전에 확인할 수 있습니다.

**2단계 사진 입력:** 영수증과 메뉴판 각각에서 촬영·항목 인식·수정·개인별 배분까지 진행할 수 있습니다. 인식 실패 시 수동 입력을 사용할 수 있습니다.

**3단계 잔돈 추첨:** 항목 부담자 중 후보를 고르고 `모두 선택`을 사용할 수 있습니다. 추첨 결과는 모든 참여자에게 동일하게 보이고 정산에 한 번만 반영됩니다.

## 14. 기술 구성과 개발 순서

Flutter로 앱부터 개발하는 방향은 확정이며, 나머지 구성은 앞선 추천을 바탕으로 한 기본안입니다. 외부 서비스 생성이나 SDK 설치는 아직 진행하지 않았습니다.

| 영역 | 기술 | 역할 및 결정 상태 |
| --- | --- | --- |
| 앱 | Flutter / Dart | 사용자 확정. 1단계 수동 입력·정산·정산 복제, 이후 촬영·미니게임 추가 |
| 상태 관리 | Riverpod | 기본안. 게스트 세션·방·지출 등 화면 상태 관리 |
| 백엔드·DB | Supabase / PostgreSQL | 기본안. 사용자 관계, 모임, 지출, 배분, 정산 결과 저장 |
| 인증·사진 저장 | Supabase Auth / Storage | 기본안. 가입 화면 없는 게스트 세션과 방 참여 권한. 사진 보관은 2단계에서 추가. 구체적인 익명 인증 구성은 구현 시 검증 |
| 동기화 | Supabase Realtime | 기본안. 친구들에게 변경 내역과 확정 결과 전달 |
| 서버 처리 | Supabase Edge Functions / TypeScript 및 DB 트랜잭션 | 기본안. 1단계 정산·복제·직접 지정 결과 검증, 이후 OCR·추첨 연동 |
| 이미지 인식 | Google Cloud Vision OCR 등 | 후보 단계. 실제 한글 영수증·메뉴판으로 정확도와 비용 검증 후 확정 |

정산 계산은 화면에서 분리하여 검증 가능한 로직으로 작성합니다. 최종 정산과 잔돈 처리 결과는 서버에서 검증·확정하고, 참여자에게 같은 결과를 전달하는 것을 기본안으로 합니다. 2단계 사진 인식 API의 비밀 키는 앱에 포함하지 않습니다.

개발 순서는 다음을 제안합니다.

1. Flutter 개발 환경과 프로젝트 구성, Android에서 기본 실행 확인
2. 수동 입력 기반 지출 등록·메뉴 배분·잔돈 직접 지정·정산 계산 구현 및 정확도 검증
3. 게스트 주의 안내, 방 생성·코드 입장·모임 공유·정산 복제 및 서버 정산 연동으로 첫 버전 완성
4. 영수증·메뉴판 촬영, 인식 결과 확인·수정 기능 추가
5. 잔돈 추첨 후보 선택·미니게임·결과 공유 추가
6. 실제 모임 시나리오 검증 후 iOS 환경에서도 빌드·기기 테스트

현재 Windows 환경에서는 Android를 먼저 검증하는 순서를 제안합니다. iOS 빌드·검증에는 별도의 macOS/Xcode 환경이 필요하며, 실제 출시 순서는 이후 결정합니다. 앱 설치 후 방 코드로 참여하는 흐름을 기본으로 설계합니다.
